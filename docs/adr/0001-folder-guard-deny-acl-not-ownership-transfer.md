# 資料夾防護採用「拒絕目前帳號 ACL 權限」，不做擁有權轉移

**狀態**：accepted

「資料夾防護」（Folder Guard）需要決定用什麼機制限制存取。考慮過兩個方案：

1. **拒絕目前帳號的 ACL 權限**（採用）：直接對目前登入帳號的 SID 加上拒絕讀寫的 ACE。不需要任何提權，App 用一般使用者權限就能做。缺點是繞過門檻很低——擁有者本人隨時能透過「內容→安全性→編輯」改回權限，不需要密碼、不會跳 UAC。
2. **擁有權轉移給隱藏系統帳號**：把資料夾擁有者改成另一個帳號，移除目前帳號的所有 ACE。繞過門檻較高，需要「取得擁有權」（系統管理員權限＋UAC），一般使用者不容易知道這個入口。但 App 本身需要一個能執行提權操作的機制（例如安裝時註冊 SYSTEM 層級的工作排程），大幅增加安裝流程與架構複雜度，且非系統管理員帳號的使用者可能整個功能都用不了。

選擇方案 1：這個功能的定位本來就是「防隨手瀏覽」而非「防蓄意繞過」（兩種機制最終都擋不住同機的系統管理員蓄意繞過，差別只在門檻高低），為了這個有限的防護力提升去換取「安裝需要系統管理員權限」「App 需要背景提權服務」這麼大的架構成本，不划算。願意接受這個功能防護力較弱的定位，並在 UI 上向使用者說明清楚。

## 拒絕的權限範圍

同一個定位下，也選擇「資料夾看得到、點進去被拒絕」（拒絕 `ReadAndExecute`／`Write`／`Delete`，不動父層列舉權限），不做成「資料夾整個消失」。後者需要額外處理父層列舉權限或搭配隱藏屬性，實作複雜度高出一截，換來的體驗（連存在都看不到）反而不符合「上鎖」這個語意本身就預期「看得到、進不去」的直覺，也不是這個功能要防的情境（防隨手瀏覽，不是防「發現有東西」）。

## 雙擊被拒絕資料夾時的畫面

維持 Windows 原生的「存取被拒」錯誤視窗，不試圖攔截、替換成 App 自訂的友善對話框。原因是這件事技術上做不到（雙擊資料夾是 `explorer.exe` 內部的瀏覽行為，不像 `.locked` 檔案有副檔名關聯機制可以掛，要攔截只能實作一整套 `IShellFolder` Shell Namespace Extension）；另一條路——用 Windows 物件存取稽核（SACL + Security Event Log）事後偵測存取被拒事件、跳出追加提示——技術上可行，但需要系統管理員權限設定稽核規則，還需要新增一個目前完全不存在的背景常駐服務才能隨時監聽，成本又繞回方案 2（擁有權轉移）被拒絕的同一個理由：為了體驗細節投入不成比例的架構成本。
